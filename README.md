## Приложение

Сервис бронирования календаря одного владельца. Гости бронируют встречи без
регистрации. Backend — ASP.NET Core 10 Minimal API; frontend — React 19,
TypeScript, Vite 8 и Mantine 9. Контракт API задаётся в TypeSpec.

### Пользовательский сценарий

1. Владелец открывает страницу /owner и создаёт тип встречи: название, описание
   и длительность.
2. Гость с главной страницы переходит к бронированию /book, выбирает тип встречи
   и свободный слот, указывает имя и подтверждает бронирование.
3. Гость видит подтверждение, владелец — предстоящую встречу в списке.

Время — Europe/Moscow, рабочие часы — Пн–Пт 10:00–18:00, окно записи — 14 дней.
Начала слотов идут каждые 30 минут; встреча должна полностью помещаться в рабочие
часы и начинаться в будущем. Пересекающиеся встречи запрещены для всех типов:
при одновременном бронировании одного интервала успешен только один запрос.

Данные хранятся в памяти и сбрасываются при перезапуске API. Авторизации нет:
страница владельца открыта всем. Термины описаны в [словаре](GLOSSARY.md).

## Установка

Установите Git и [mise](https://mise.jdx.dev/getting-started.html), затем выполните:

```bash
git clone https://github.com/MeNn13/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise trust
mise install
mise run install
```

Для локального запуска база данных, секреты и переменные окружения не нужны.
При первом запуске браузерных тестов установите Chromium: `mise exec -- npx playwright install chromium`.

## Запуск и проверки

```bash
mise run dev
```

- Frontend: <http://127.0.0.1:5173>.
- API: <http://127.0.0.1:5000/api/health>.

```bash
mise run check
```

Полная локальная проверка обязательна перед пушем; CI вызывает ту же команду.
Автоисправления — `mise run fix`. Подробности проверок и управления фоновыми
процессами — в [руководстве разработчика](docs/development.md).

## Аудит производительности

[Lighthouse audit](.github/workflows/lighthouse-audit.yml) запускается ежедневно
в 06:17 по Москве. В GitHub Actions его можно запустить вручную из `main`.
Режим `live` проверяет страницу бронирования по переменной репозитория `APP_URL`.
Режим `training` использует синтетическое измерение для демонстрации выпуска задачи.

Отчёт хранится 14 дней в артефакте `lighthouse-report`. OpenCode анализирует
проверки с измеримой потенциальной экономией. Издатель создаёт отдельный issue
по новой находке и добавляет в него ссылку на прогон. При повторе Summary
ссылается на исходный issue, включая закрытые задачи. Вывод без находок или
статус «нет данных» сохраняется в постоянном issue аудита из `AUDIT_STATUS_ISSUE`.
Одинаковые статусы подряд публикуются один раз.

Порядок настройки и приёмки описан в [руководстве по GitHub-агенту](docs/github-agent.md#аудит-производительности).

### Результаты ручных прогонов

- [Первый `live` из `main`](https://github.com/MeNn13/booking-calendar-opencode-v1-acceptance/actions/runs/45417700302)
  проверил страницу бронирования `/book` на Render. Lighthouse дал 97 из 100
  и сохранил исходный JSON в артефакте `lighthouse-report`.
- [Повторный `live`](https://github.com/MeNn13/booking-calendar-opencode-v1-acceptance/actions/runs/45420316020)
  и [последний `training`](https://github.com/MeNn13/booking-calendar-opencode-v1-acceptance/actions/runs/45438505048)
  сохранили отчёты. На этапе анализа основная и резервная модели OpenCode
  вернули `provider.free-limit` (HTTP 429). Приёмка публикации остаётся открытой.
  После восстановления лимита нужно получить вывод агента, создать учебный
  issue и подтвердить отсутствие дубля вторым учебным прогоном.
- Для итогов без новой находки настроен [журнал аудита #35](https://github.com/MeNn13/booking-calendar-opencode-v1-acceptance/issues/35).

### Личные выводы о работе GitHub-агента

Ревью и триаж в GitHub кажутся мне интересными сценариями. К реализации внутри
GitHub я отношусь скептически и предпочитаю для неё локального агента. Аудит по
расписанию тоже считаю важным. Он помогает вовремя обнаруживать проблемы в приложении.

Больше всего уточнений потребовали права модели и постановка задач. Я хотел,
чтобы модель могла анализировать проект без доступа на редактирование, а система
работала предсказуемее. В процессе стало понятно, что на такую реализацию нужно
больше времени, чем у меня было. Поэтому я остановился на более простом варианте
работы модели в GitHub. Чтобы прийти к реализации, которую я себе представляю,
мне нужно больше времени на эксперименты и больше доступных запусков модели.

1. Для независимого ревью я бы запускал модель без памяти о проекте и о ходе
   реализации. В моих проверках более простая модель в OpenCode находила замечания,
   которые пропустила GPT-6.2 Astra с уровнем рассуждений `high`.
2. В реальном проекте я бы отказался от `/implement-spec`, `/implement` и других
   сценариев реализации внутри GitHub. Я хочу использовать GitHub для контроля
   версий и оставлять редактирование файлов в локальной среде разработки.
3. В реальный проект я бы добавил ревью и аудит по расписанию. Это позволило бы
   сократить время на повторяющиеся проверки.
